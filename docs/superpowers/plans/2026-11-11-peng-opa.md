# peng-opa Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build peng-opa, a multi-tenant OPA-powered policy management SaaS with a no-code rule builder, decision API, template gallery, usage dashboard and demo mode.

**Architecture:** A NestJS API owns all state in Postgres and pushes compiled Rego to one internal OPA server through a single `OpaGateway`. Customers call `POST /v1/decide/:policyKey` with a Bearer API key; the workspace always comes from the key. A React SPA (served by Nest) is the only UI.

**Tech Stack:** pnpm workspaces, TypeScript, NestJS, Prisma, PostgreSQL 16, Better Auth, OPA 1.x, React + Vite + TanStack Router/Query + shadcn/ui + Tailwind + Monaco + Recharts, Vitest, Supertest, Testcontainers, Playwright, Docker Compose, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-11-peng-opa-design.md`

## Global Constraints

- Layout: `apps/server`, `apps/web`, `packages/shared` (package name `@peng/shared`).
- Every tenant-owned table has `workspaceId`; every query on those tables is scoped through the workspace Prisma extension (Task 5). No exceptions.
- The public decide endpoint works out the workspace only from the API key; any workspace/tenant id in the body is ignored.
- OPA package `t_<workspaceShortId>.<policy_key_snake>`; OPA policy id `t_<shortId>/<policyKey>`; draft package `t_<shortId>._draft_<policyShortId>`.
- `Policy.key`: `^[a-z0-9-]{3,60}$`, unique per workspace, immutable after the first publish.
- Field path segments: `^[a-z][a-z0-9_]*$`, joined by `.`.
- Rules: first match wins; one `all`/`any` per rule; no nested groups.
- Decide limits: body ≤ 64 KB; batch ≤ 100 inputs; OPA timeout 2 s; rate limit default 50 rps per workspace (`RATE_LIMIT_RPS`).
- Audit flush every 1 s or 200 records; sync every 60 s; draft sweep hourly (unused > 1 h).
- Draft autosave debounce 1.5 s.
- Demo: 4 live policies, ~3,000 decisions over 14 days, simulator ~1 rps auto-off after 10 min.
- Error body for the public API: `{ "error": { "code": string, "message": string } }`.
- Roles: OWNER > EDITOR > VIEWER (VIEWER: read + Try-it only).
- Allowed/Denied always rendered as green ✅ / red ⛔ chips.
- Every UI task follows ui-consistency: `finding-patterns` → `implementing` → `verifying`. Task 19 sets the first patterns; later UI tasks follow them.
- Out of scope: billing, Arabic/RTL, SSO/SAML, raw Rego editing, nested groups, external data, bundle server, outbound webhooks, sub-path deploy.

## Review Focus

1. **Quotes, backslashes or newlines in rule values / reasons** (e.g. `O'Brien "VIP"\n`) must compile to valid Rego and match literally, never inject code. → Task 3 test `escapes_hostile_strings`.
2. **Numeric string sent for a number field** (`"total": "620"`) must return 422 `invalid_input`, not silently fail to match. → Task 12 test `numeric_string_is_type_error`, Task 13 e2e.
3. **Deleting a field or outcome still used by a rule** must block publishing with a clear issue, not produce Rego that references nothing. → Task 2 test `field_removed_but_used`.
4. **Two publishes of the same policy at the same moment** must produce v(n) and v(n+1) or one 409, never a duplicate-key 500. → Task 10 test `concurrent_publish`.
5. **OPA restarts while the app is running** — decisions must recover within one sync cycle without anyone republishing. → Task 11 test `recovers_after_opa_restart`.
